# 开发规范
## 1. 分支管理规范
1. `main`：最终交付稳定分支，禁止直接提交代码；验收前由 dev 合并进入
2. `dev`：开发主分支，所有人开发基准分支
3. 功能分支：从 dev 拉出，命名格式 `feat/功能名称`
    示例：`feat/image-upload`、`feat/history-record`
4. Bug修复分支：`fix/问题描述`

> 流程：dev → 新建feat分支开发 → 自测完成 → 合并回dev → 删除功能分支

## 2. Git Commit 提交规范
格式：`类型: 简短描述`
- chore：工程配置、目录、Docker、文档、脚手架调整
- feat：新增功能
- fix：bug修复
- docs：文档修改
- refactor：代码重构，无功能变更

示例：
`feat: 实现图片URL上传功能`
`fix: 修复大模型请求超时问题`
`chore: 更新docker数据库配置`

## 3. 环境配置规范
1. 仅提交 `.env.example`，禁止提交带有真实密钥的 `.env`
2. 所有人本地复制 `.env.example` → `.env`，自行填充密钥
3. 禁止硬编码数据库密码、QWEN_API_KEY写在业务代码内

## 4. 文件与代码规范
1. 不提交：node_modules、日志、.env、编辑器配置、数据库持久缓存
2. 前后端命名统一，数据表字段名称前后端保持一致
3. 新增SQL表结构修改，统一更新 `docker/mysql/init.sql`

## 5. 协作约定
1. 每天基于 dev 拉取最新代码，避免大量代码冲突
2. 接口改动、数据表结构改动提前沟通，同步双方
3. 重大配置变更由交付负责人统一更新仓库模板
